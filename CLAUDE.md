# CLAUDE.md — The Longevity Centre

Project context for future Claude Code sessions. Read this first before
making changes.

## Project

- **Site:** The Longevity Centre (`thelongevitycentre.co`)
- **Stack:** Vite + React 19 + TypeScript + Tailwind CSS, with GSAP +
  Lenis for motion
- **Source:** `tac-preview/` (the app lives here; the repo root is one
  level up at `the-longevity-centre/`)
- **Hosting:** Hostinger shared (Apache + LiteSpeed). Deploy by uploading
  a zip of the built `dist/` folder into `public_html/` and extracting.
- **Domain migration:** The new TLC site is the successor to the old
  `theantiagingcentre.com` (TAC). The old domain's `.htaccess` 301s every
  request to `thelongevitycentre.co/<same-path>`. Many of the redirects,
  blog routes and SEO landing pages exist to preserve the old domain's
  search ranking through that 301.

## Quick commands

```bash
cd tac-preview
npm install              # first time
npm run dev              # local dev server on :5180
npm run build            # production build to dist/  + per-route HTML injection
npx tsc --noEmit         # type check (no emit)
```

The `build` script chains three steps:
1. `tsc -b` — type check
2. `vite build` — bundle JS/CSS, copy `public/*` to `dist/`
3. `node scripts/inject-meta.cjs` — generate 73 per-route `dist/<path>/index.html`
   files with the correct `<title>`, `<meta description>`, `<link canonical>`
   and a `<noscript>` content block. See **SEO pre-baking** below.

## Routing — `src/routes.tsx`

The router is hand-rolled (no react-router). Three things live in this
file:

1. **`REDIRECTS`** — flat key→value map of old paths to new ones. Runs
   synchronously on module load via `applyRedirect()` so the very first
   render already sees the corrected path. Used for the legacy
   theantiagingcentre.com URL space (117 entries — programmes, diagnostics
   slug renames, skin-aesthetics root → nested, location-targeted SEO
   pages, zero-traffic topical blog redirects).
2. **`ROUTES`** — ordered table of exact / prefix path matches mapped
   to lazy-loaded page components.
3. **`BLOG_SLUGS`** / **`LANDING_SLUGS`** — arrays that spread into
   `ROUTES` to give each migrated blog post / SEO landing its own
   root-level path matching the legacy URL.

When adding a blog, edit `src/lib/blogs.ts` AND add the slug to
`BLOG_SLUGS` — they must stay in lockstep.

## Build output (`dist/`)

After `npm run build`, the upload-ready output is in `tac-preview/dist/`.
It includes:

- All hashed JS/CSS chunks in `assets/`
- All public assets copied from `public/`: blog/, landings/, longevity/,
  team/, videos/, etc.
- **`.htaccess`** at the root — bundled because Vite copies `public/.htaccess`
  through to `dist/.htaccess`. Critical for SPA routing on Apache.
- **73 per-route `<path>/index.html`** files generated by inject-meta —
  one per indexable URL, with route-specific meta tags + a `<noscript>`
  body block containing real content (see **SEO pre-baking** below).

Total: ~381 files, ~96 MB zipped.

## SEO pre-baking — `scripts/inject-meta.cjs`

**The single biggest SEO mechanism in this project.** Post-build step that
fixes a critical issue: crawlers that don't execute JavaScript (Ahrefs on
the default plan, Bing, social-share scrapers, the slow path of Googlebot)
otherwise saw every URL as identical — same `<title>`, same canonical
pointing to `/`, empty `<h1>`, 14 words of content. Google would dedupe
all 70+ pages into the homepage.

What the script does:

1. **Bundles each `src/lib/*.ts` data file to CJS via esbuild** (added as
   an explicit devDependency just so Node's resolver can `require()` it
   from the script — Vite's transitive copy isn't reachable).
2. **Builds a `URL → { title, description, content }` map** from BLOGS,
   LANDINGS, PROGRAMS, CENTRES, DIAGNOSTICS, SKIN_TREATMENTS plus a
   handwritten list for the static top-level pages (`/about-us`, `/contact`,
   index pages, etc.).
3. **For every entry, takes `dist/index.html` as the template, swaps in
   the route-specific tags** — `<title>`, `<meta name="description">`,
   `<link rel="canonical">`, og:title, og:description, og:url,
   twitter:title, twitter:description — and **injects a `<noscript>` block
   right after `<div id="root"></div>`** containing:
   - Primary site navigation (8 main pages → real internal links from
     every page, fixes "orphan" / "no inlinks" flag)
   - Breadcrumb back to home
   - Page-specific HTML: H1, intro, full content per route type
     (blogs render markdown to HTML, programmes render designed-for /
     diagnostics / care-model / outcomes lists, etc.)
   - Site footer with brand sentence, contact, privacy/terms links
4. **Writes `dist/<route>/index.html`** for each entry. Body remains
   `<div id="root">` so React still hydrates from scratch on the client —
   the noscript block is invisible to JS-enabled browsers (no visual flash
   for real users) but rendered as ordinary HTML by JS-disabled crawlers.

Includes a minimal markdown → HTML converter (`md2html` + `inlineMd`)
inside the script so the noscript content for blogs/landings is readable
HTML, not a wall of markdown syntax.

When you add a new route type or new top-level page, update inject-meta.cjs
in the same commit — otherwise the new page won't get its own per-route
HTML and SEO will silently regress on it.

## Deploy to Hostinger

```bash
cd tac-preview
npm run build
# Now zip dist/ contents. PowerShell's Compress-Archive writes Windows
# backslashes that Linux can't extract into folders, so use Node + archiver.
```

To create the deploy zip on Windows:

```bash
npm install --no-save archiver
node make-zip.cjs   # ad-hoc; see prior commits for the script body
```

The zip needs:
- All ~381 files from `dist/`
- Forward-slash paths (Linux compatibility)
- `.htaccess` at root (Hostinger's File Manager hides dot files by default
  — enable "Show hidden files" in its settings gear icon to verify)

Upload + extract into Hostinger `public_html/` root. Hostinger's File
Manager can time out on extraction of 90+ MB zips with 381 files. If that
happens, use FileZilla / FTP for direct file upload instead, or contact
the user — they have credentials.

## `.htaccess` — critical config

Lives at `public/.htaccess` (bundled into `dist/.htaccess` by the build).
Three non-obvious rules in it:

1. **`DirectorySlash Off`** — mod_dir would otherwise 301-redirect
   `/skin-aesthetics` → `/skin-aesthetics/` because that path is a
   real folder on disk (containing skin treatment images). The redirect
   happens before our SPA rewrite, so we lose the chance to send the
   request to React Router.
2. **Per-route pre-baked index.html lookup** — before falling back to the
   SPA root, the rewrite checks `%{DOCUMENT_ROOT}%{REQUEST_URI}/index.html`.
   If it exists, that file is served (with the correct title / canonical
   / noscript content). Otherwise the SPA fallback runs.
3. **`RewriteCond %{REQUEST_FILENAME} !-f`** only (no `!-d`) — we
   deliberately **do not** skip the rewrite for directories. The build
   contains folders whose names collide with React routes (`blog/`,
   `diagnostics/`, `skin-aesthetics/`). With `!-d` those folder requests
   land on Apache's directory handler, find no `index.html`, and return
   `403 Forbidden`. By only checking for real files, we correctly
   rewrite folder-name requests to `index.html` so React Router resolves
   them client-side, while individual asset files
   (`/skin-aesthetics/01-prp-acp.jpg`) still serve directly because
   they ARE real files.

## React 19 gotchas

- **react-markdown 10.x does not work** with React 19 in this project
  (Invalid hook call errors fire globally, breaking every lazy page).
  We ship our own `src/lib/markdown.tsx` instead — a minimal renderer
  for the markdown subset the migrated blog content uses (headings,
  lists, links, **bold**, *italic*, `code`, blockquotes, `---`).
- **Vite dev cache header** is set to `no-cache, no-store, must-revalidate`
  in `vite.config.ts` `server.headers`. The default `max-age=3600` once
  made an "Invalid hook call" survive on disk long after the fix was
  shipped — debugging took hours. Don't re-enable dev caching.

## SEO migration from theantiagingcentre.com

The old TAC site had ~155 indexed URLs. Coverage on the new site:

- **25 blog posts** migrated as full content at the same root-level
  URLs (`/10-tips-for-good-health` etc.). See `BLOG_SLUGS` in
  `routes.tsx` and `BLOGS` in `lib/blogs.ts`.
- **5 SEO landing pages** migrated as full content (`LANDING_SLUGS`
  + `LANDINGS` in `lib/landings.ts`).
- **117 legacy URLs** mapped via `REDIRECTS` in `routes.tsx`. Grouped
  by category in the file with comments — programmes, diagnostics
  (slug renames like `bca` → `body-composition`), skin-aesthetics root
  → nested, location-targeted SEO pages, intent-targeted SEO pages,
  and zero-traffic topical blog redirects.
- **Old-domain `.htaccess`** on `theantiagingcentre.com` 301s every
  request to `https://thelongevitycentre.co/<same-path>`. Combined with
  the new-domain REDIRECTS map, a request to e.g.
  `theantiagingcentre.com/metabolic` ends up on
  `thelongevitycentre.co/programs/metabolic-weight-loss`.

When adding NEW redirects: append to the `REDIRECTS` map. When changing
a migrated blog's slug: don't — keep the slug stable to preserve the
ranking the old domain has.

## What NOT to add

- ❌ `react-markdown` (breaks React 19 — see above)
- ❌ `react-router` (we have a 50-line router that works fine)
- ❌ Heavy dev cache headers (broke debugging once, will again)
- ❌ Three skin treatments that briefly existed and were removed per
  client: `cool-sculpting`, `viora-rf`, `wonder-muscle`. Their legacy
  redirects now point to `/skin-aesthetics` index.
- ❌ Removing the `<noscript>` block from inject-meta.cjs — that block
  is what makes non-JS-rendering crawlers see real page content. The
  Ahrefs Health Score baseline before it was 19/100; the block is
  the single largest lever pulling that number up.

## Known follow-ups (deferred)

- **29 `<img>` tags use `src={item.image}` (dynamic) and don't have
  width/height** — they all source from data records in `src/lib/*.ts`.
  Adding intrinsic `width` / `height` fields to the data interfaces
  (BLOGS, CENTRES, PROGRAMS, etc.) and threading them through the JSX
  would close out the last batch of Lighthouse CLS warnings. The 24
  static-`src` `<img>` tags already have dimensions baked in.
- **Hosting auto-deploy** — currently every deploy is a manual zip
  upload + extract in Hostinger File Manager (which has been flaky on
  large extractions). Setting up either Hostinger's built-in Git Deploy
  (Premium+ plans) or a small GitHub Actions FTP-deploy workflow would
  remove that friction. Discussed with user — they preferred manual for
  the migration sprint, will revisit afterwards.
